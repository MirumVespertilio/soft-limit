# Техническое задание: Telegram Mini App с рулеткой контента

**Версия:** 0.3  
**Статус:** этап проектирования завершён; реализация ещё не начата.  
**Основной язык backend:** Python.  
**Среда разработки:** локально на Windows; затем пробный деплой на бесплатный хостинг, если его ограничений хватит.

## 1. Цель проекта

Создать собственный Telegram-бот с Mini App, в котором пользователь крутит анимированное колесо рулетки и получает карточки с фотографиями или видео AI-модели. Владелец управляет контентом, колесом, балансами и статистикой через веб-админку, открывающуюся внутри того же Mini App.

Проект разрабатывается самостоятельно: не использовать закрытый код сторонних сервисов. Первая версия должна работать без реальных платежей, чтобы можно было проверить игровой процесс и админку.

## 2. Принятые архитектурные решения

- Telegram-бот: **aiogram 3**.
- Backend и API: **FastAPI**.
- Работа с базой данных: **SQLAlchemy 2** и **Alembic**.
- Локальная база на первом этапе: **SQLite**; перед полноценным размещением — переход на **PostgreSQL**, если выбранный хостинг это поддерживает.
- Интерфейс Mini App: **HTML, CSS и JavaScript**. React и Node.js для первой версии не требуются.
- Админка встроена в тот же Mini App и показывается на основании проверенной роли Telegram-аккаунта.
- Оригиналы фотографий и видео по возможности хранятся на стороне Telegram. В БД сохраняются Telegram `file_id` и метаданные. Способ доставки медиа в Mini App изолируется за отдельным модулем, чтобы позднее можно было подключить внешнее хранилище.
- Реальные платежи в MVP не реализуются. Архитектура заказов и платежей должна допускать расширение в будущем, но никаких недействующих способов оплаты в интерфейсе пока нет.
- Telegram Serverless не используем: он не является средой для запуска нашего Python/FastAPI-приложения.

## 3. Роли и авторизация

### 3.1. Владелец

Владелец входит через Telegram и видит админку. Его Telegram ID задаётся в конфигурации сервера через переменные окружения или настройки развёртывания.

### 3.2. Пользователь

Любой другой Telegram-аккаунт видит игровую часть Mini App.

### 3.3. Требования безопасности

- Backend проверяет подпись Telegram `initData` и срок её актуальности.
- Нельзя определять владельца только по Telegram ID, присланному JavaScript-кодом без серверной проверки.
- Каждая административная операция повторно проверяет роль на backend.
- Токен Telegram-бота хранится только на сервере и не передаётся в браузер.
- Секреты хранятся в переменных окружения; в репозитории есть только `.env.example` без настоящих токенов.

Документация: [Telegram Mini Apps](https://core.telegram.org/bots/webapps).

## 4. Основной игровой процесс

### 4.1. Балансы

В приложении существует два отображаемых ресурса:

1. **Звёзды** — во время бета-тестирования это тестовый баланс, не являющийся настоящими Telegram Stars и не имеющий денежной стоимости. Владелец вручную начисляет его пользователям.
2. **Доступные спины** — число прокруток, которыми пользователь располагает в данный момент.

Отдельного типа баланса или отдельного счётчика «дополнительных бесплатных прокруток» не создаётся. Приветственный спин, купленные за тестовые звёзды спины и спины, вручную добавленные владельцем, пополняют один общий баланс доступных спинов. Источник каждого изменения сохраняется в журнале операций.

Обычный спин расходует **один доступный спин**, а не звёзды напрямую. Тестовые звёзды списываются в момент покупки пакета спинов.

### 4.2. Приветственный спин

- При первой регистрации аккаунта система один раз начисляет пользователю **один спин** на общий баланс доступных спинов.
- Пользователь сначала видит полноценное основное колесо со всеми видимыми активными секторами, как и при обычном спине.
- Для самой первой прокрутки результат выбирается сервером только из списка карточек, который владелец предварительно настроил в админке.
- Пользователю показывается полноценная анимация колеса. Оно останавливается на секторе выбранного сервером приза; мгновенная выдача карточки без вращения не допускается.
- После использования приветственного спина последующие спины выбираются по обычным настройкам колеса.
- Приветственный спин нельзя получить повторно при перезапуске Mini App, повторном `/start`, очистке браузерного кэша или входе с другого устройства под тем же Telegram-аккаунтом.
- В приветственный пул можно добавить несколько карточек. Сервер выбирает одну из них; в первой версии карточки внутри пула имеют равный шанс, если владелец не задаёт отдельные веса в будущей версии.
- Все карточки из приветственного пула должны соответствовать секторам, отображаемым на основном колесе. Если карточку убирают из активных секторов, админка предупреждает владельца и не позволяет оставить некорректную конфигурацию.
- Пользовательский интерфейс не должен обещать равные шансы, если фактическая механика их не обеспечивает. Если в дальнейшем на экране показываются численные вероятности, они обязаны соответствовать реальным правилам выбора.

Результат выбирает сервер, не фронтенд. Сначала в одной транзакции базы данных проверяется баланс, выбирается награда, уменьшается число доступных спинов и сохраняется результат. После успешного сохранения интерфейс запускает анимацию к нужному сектору.

### 4.3. Обычная рулетка

- Полноценное анимированное колесо с секторами.
- Каждый сектор связан с карточкой контента и имеет вес вероятности.
- Владелец может добавлять, редактировать, включать и отключать секторы, а также менять их веса.
- Владелец задаёт цену пакетов спинов в тестовых звёздах.
- Результат выбирается сервером на основании активной конфигурации колеса.
- Анимация показывает результат, уже зафиксированный сервером; клиент не может выбрать или подменить выпавший приз.
- Повтор одного запроса с тем же ключом идемпотентности не должен повторно списывать спин или выдавать приз.

### 4.4. Покупка спинов в бета-версии

Реальных платежей нет. Владелец вручную начисляет пользователю тестовые звёзды. Пользователь может потратить их на доступные пакеты спинов.

Для пакета задаются:

- название;
- количество спинов;
- цена в тестовых звёздах;
- активность и порядок показа.

Покупка пакета атомарно списывает тестовые звёзды и увеличивает общий баланс доступных спинов. Если средств не хватает, покупка не выполняется. Двойной запрос не должен повторно списывать тестовые звёзды или повторно начислять спины.

### 4.5. Коллекция и история

Пользователь может открыть коллекцию выигранного контента и посмотреть доступные ему карточки. В истории сохраняются дата, вид спина, выпавший приз и статус выдачи медиа.

У пользователя **не показывается общая сумма потраченных звёзд** и другие агрегированные показатели его расходов.

## 5. Админка

Админка открывается в том же Mini App, но только для владельца.

### 5.1. Медиатека и карточки

- Загрузка фотографий и видео.
- Создание, редактирование, публикация и отключение карточек.
- Название, описание, тип контента, превью, файлы оригинала и статус.
- Одна карточка может содержать несколько файлов, например обложку и оригинальное видео.

### 5.2. Настройки колеса

- Управление секторами и связанными карточками.
- Настройка веса каждого активного сектора.
- Настройка цены и списка пакетов спинов.
- Выбор нескольких карточек для приветственного пула.
- Проверка конфигурации, чтобы в приветственном пуле не оставались отключённые или отсутствующие на видимом колесе карточки.

### 5.3. Пользователи и ресурсы

Поиск пользователя по Telegram ID. В карточке пользователя администратор видит его тестовый баланс звёзд, доступные спины, историю начислений, покупок пакетов и прокруток.

Администратор может:

- начислить или скорректировать тестовые звёзды;
- начислить или скорректировать общее количество доступных спинов;
- указать причину операции.

Не создавать отдельный пользовательский баланс для «бесплатных спинов». Ручное добавление спинов меняет тот же общий баланс, но в журнале операций имеет источник `admin_adjustment`.

### 5.4. Финансовый дашборд

В админке нужен отдельный дашборд статистики, не доступный обычным пользователям.

После подключения реальных платежей дашборд должен показывать:

- общую сумму подтверждённой выручки за выбранный период и за всё время;
- количество оплаченных заказов и средний чек;
- выручку по пользователям — сколько реальных платежей подтвердил каждый пользователь;
- продажи пакетов спинов и покупки конкретного контента;
- доходы по типам продукта и, если позднее появятся разрешённые провайдеры, по способам оплаты;
- возвраты и отменённые платежи отдельно от успешных поступлений;
- базовые игровые метрики: число пользователей, прокруток, выигранных карточек и активность.

На бета-этапе реальные доходы должны отображаться как нулевые, а статистика по тестовым звёздам — отдельно и с явной пометкой **«тестовые данные, не выручка»**. Ручные начисления тестовых звёзд нельзя учитывать как доход.

Показатели общих расходов пользователя доступны только в админке, не в пользовательском интерфейсе.

## 6. Хранение, сжатие и выдача медиа

### 6.1. Общее решение

По возможности используем Telegram как хранилище оригиналов. Бот загружает файл в приватный канал-библиотеку (бот должен иметь право публиковать туда материалы) и сохраняет `file_id`, `file_unique_id`, тип, размер и связь с карточкой. `file_id` можно повторно использовать тем же ботом; он не является URL, который можно безопасно вставить в браузер.

В БД хранится абстрактный тип источника и идентификаторы, чтобы впоследствии можно было добавить объектное хранилище без изменения игровой логики. Наличие `file_id` не отменяет резервное копирование важной конфигурации и метаданных.

### 6.2. Фотографии

При загрузке фотографии backend обрабатывает её временно в памяти или во временной папке, затем загружает оптимизированную версию в Telegram.

Правила обработки:

- не ухудшать качество без необходимости;
- сначала пробовать умеренное сжатие, а при необходимости постепенно уменьшать качество или размеры;
- целевой размер файла — с запасом ниже лимита Bot API для `sendPhoto` (ориентир около 9 МБ, а не попытка упереться точно в предел);
- не увеличивать маленькие изображения;
- сохранять корректную ориентацию, метаданные размеров и исходное соотношение сторон;
- для обычных фотографий использовать JPEG с качеством примерно 88–92 как начальную точку, подбирая параметры по итоговому размеру;
- для прозрачных изображений не применять JPEG без проверки: при необходимости сохранять PNG/иной поддерживаемый вариант или делать отдельный вариант для предпросмотра.

Если владелец не хочет терять оригинальное качество, можно дополнительно сохранять оригинал как документ в Telegram (в пределах лимитов Bot API) и использовать сжатый вариант для быстрого предпросмотра. Это необязательная оптимизация MVP; на первом этапе важнее простота и надёжная выдача.

Для показа фотографии прямо в Mini App используется защищённый маршрут backend: токен бота никогда не выдаётся клиенту. Превью небольшие, поэтому их можно отдавать через этот маршрут. Нужно избегать загрузки оригиналов полного разрешения в список карточек.

### 6.3. Видео

Предлагаемый вариант с минимальными расходами и без отдельного видеохостинга:

1. Владелец загружает видео и отдельное изображение-обложку (превью).
2. Видео сохраняется на стороне Telegram; в БД остаётся его `file_id` и метаданные.
3. В Mini App на секторе и странице результата отображаются обложка, название и информация о выигрыше. Автовоспроизведение полного оригинала в браузере не требуется.
4. После выигрыша бот отправляет видео в личный чат пользователя методом `sendVideo`, используя сохранённый `file_id`. В Mini App показывается статус отправки и понятная кнопка/подсказка для перехода в чат бота.
5. При повторном открытии полученной видеокарточки пользователь может запросить повторную отправку видео. Каждая отправка фиксируется, чтобы повторные сетевые запросы не создавали случайные дубли.

На первом этапе разумно ограничить загружаемые видео 50 МБ и использовать распространённый формат MP4 с кодеком H.264. Стандартный Bot API позволяет боту отправлять видео до 50 МБ. Если файл больше или не поддерживается, админка должна показать понятную ошибку и предложить сжатие/конвертацию или отдельное хранилище в будущей версии. Не запускать тяжёлое перекодирование на бесплатном хостинге без проверки его ресурсов.

Для MVP проще попросить владельца вручную загрузить обложку, чем обязательно генерировать её через FFmpeg на сервере. Автоматическую генерацию можно добавить позже.

### 6.4. Лимиты и безопасность медиа

- Обычный Bot API ограничивает скачивание через `getFile` файлами до 20 МБ; отправка файлов ботом поддерживает до 50 МБ. Условия могут меняться, перед реализацией лимиты следует повторно проверить.
- Не передавать Bot API token на frontend и не создавать общедоступные URL, содержащие токен.
- Не допускать выдачу оригинала до выигрыша/покупки или без соответствующего права доступа.
- В случае ошибки отправки видео результат спина не откатывается и не выдаётся заново. Доставка повторяется отдельно.
- Использовать журнал/очередь доставки в БД, чтобы можно было повторить неудачную отправку видео после временного сбоя.

Документация Telegram: [Bot API](https://core.telegram.org/bots/api), [FAQ — работа с файлами и file_id](https://core.telegram.org/bots/faq).

## 7. Будущая платёжная архитектура

### 7.1. Сейчас

Настоящие платежи не реализуются. Тестовые звёзды начисляются владельцем вручную, пользователь покупает на них тестовые пакеты спинов, а спины расходуются при вращении колеса.

### 7.2. Позже

Первый реальный способ оплаты — Telegram Stars (`XTR`). До успешного подтверждения оплаты сервером заказ нельзя считать оплаченным и нельзя выдавать купленный ресурс. Повторные webhook/update-события не должны приводить к повторной выдаче заказа.

В БД заранее предусматриваются заказы и попытки оплаты, независимые от логики колеса и контента. Это позволит позже добавлять новые адаптеры платёжных провайдеров без изменения игровой логики. Интеграция Dropp.fans в этой версии **не реализуется, не активируется и не показывается пользователям**.

Важно: по действующим правилам Telegram цифровые товары и услуги внутри ботов и Mini Apps оплачиваются исключительно Telegram Stars. Поэтому возможность будущей оплаты конкретного контента картой через Dropp.fans должна быть отдельным предметом проверки допустимого сценария и применимых правил; техническое наличие API не означает, что такой способ разрешён внутри Telegram.

Документация: [Telegram Stars для цифровых товаров и услуг](https://core.telegram.org/bots/payments-stars).

## 8. Схема базы данных

Ниже — рекомендуемый состав таблиц для первой схемы. Типы полей и индексы уточняются при создании моделей SQLAlchemy.

| Таблица | Назначение и ключевые поля |
|---|---|
| `users` | `id`, уникальный `telegram_id`, username/имя при наличии, дата регистрации, `welcome_spin_granted_at`, `welcome_spin_used_at` |
| `user_wallets` | `user_id`, `test_stars_balance`, `spins_balance`, `updated_at` |
| `wallet_transactions` | пользователь, ресурс (`TEST_STARS`/`SPINS`), знаковая дельта, тип/причина, кто выполнил, ссылка на связанную операцию, дата |
| `media_assets` | тип файла, Telegram `file_id`, `file_unique_id`, MIME-тип, размер, имя, размеры изображения/видео, provider, состояние обработки |
| `content_items` | название, описание, статус, тип контента, дата создания |
| `content_item_media` | связь карточки с файлами, роль файла (`preview`, `main`, `original`), порядок |
| `wheels` | название, статус, цена/настройки, дата изменения |
| `wheel_segments` | колесо, карточка, порядок/подпись сектора, вес вероятности, активность |
| `welcome_reward_items` | карточки, разрешённые для первого спина; уникальная связь карточка-список |
| `spin_packages` | название, количество спинов, цена в тестовых звёздах, активность и порядок |
| `spin_purchases` | пользователь, пакет/снимок цены, потраченные тестовые звёзды, добавленные спины, idempotency key, дата |
| `spins` | пользователь, колесо, тип результата (`welcome`/`standard`), выпавшая карточка/сектор, стоимость в ресурсах (обычно 1 спин), idempotency key, дата |
| `user_inventory` | пользователь, карточка, источник получения, ссылка на спин/заказ/админскую выдачу, дата |
| `media_deliveries` | пользователь, медиа, связанный выигрыш, статус отправки, Telegram message ID, число попыток, ошибка/дата последней попытки |
| `admin_audit_log` | администратор, действие, целевая сущность/ID, необходимые детали, дата |
| `orders` | будущий заказ пользователя: тип продукта, продукт/количество, сумма, валюта, статус, даты |
| `payment_attempts` | будущий провайдер, внешний ID, статус, сумма и валюта, данные идемпотентности, подтверждение/ошибка |

### Важные ограничения БД

- `users.telegram_id` уникален.
- На одного пользователя приходится одна запись `user_wallets`.
- Приветственный спин начисляется только один раз: операция начисления и соответствующая запись/флаг должны быть защищены уникальным ограничением и транзакцией.
- `spins.idempotency_key` уникален в подходящей области (например, в сочетании с пользователем), чтобы повтор запроса возвращал существующий результат.
- Балансы не могут становиться отрицательными.
- Изменение баланса и запись в `wallet_transactions` проводятся одной транзакцией БД.
- Покупка пакета одновременно списывает тестовые звёзды, увеличивает `spins_balance` и сохраняет покупку.
- Прокрутка одновременно уменьшает `spins_balance`, записывает выигрыш и создаёт запись инвентаря. Все изменения либо фиксируются вместе, либо не фиксируются вообще.
- Историю платежей, начислений и списаний не использовать для показа пользователю общей суммы расходов.
- Для финансового дашборда реальные подтверждённые платежи и тестовые операции должны быть разделены по статусу и типу ресурса.

## 9. API первой версии

Все адреса ниже предварительные. Эндпоинты требуют валидной пользовательской сессии, а маршруты `/admin/*` дополнительно проверяют роль владельца.

### 9.1. Авторизация и пользователь

| Метод | Эндпоинт | Назначение |
|---|---|---|
| `POST` | `/api/v1/auth/telegram` | Проверить Telegram `initData`, создать/обновить пользователя и сессию; при первой регистрации начислить приветственный спин ровно один раз |
| `GET` | `/api/v1/me` | Получить профиль, тестовые звёзды и общий баланс доступных спинов |
| `GET` | `/api/v1/config` | Получить общие настройки интерфейса |

### 9.2. Колесо, спины и баланс

| Метод | Эндпоинт | Назначение |
|---|---|---|
| `GET` | `/api/v1/wheel` | Получить видимые активные секторы колеса и публичные данные карточек-призов |
| `GET` | `/api/v1/spin-packages` | Получить активные пакеты, количество спинов и цену в тестовых звёздах |
| `POST` | `/api/v1/spin-purchases` | Купить пакет за тестовые звёзды: атомарно списать звёзды и добавить спины |
| `POST` | `/api/v1/spins` | Выполнить один спин, списать один доступный спин и получить сохранённый результат |
| `GET` | `/api/v1/spins/{spin_id}` | Получить статус и результат уже запущенного спина |
| `GET` | `/api/v1/spins/history` | История спинов пользователя |
| `GET` | `/api/v1/inventory` | Получить коллекцию карточек пользователя |
| `GET` | `/api/v1/inventory/{item_id}` | Получить доступную пользователю карточку и действия для получения медиа |

Для `POST /api/v1/spins` клиент посылает ключ идемпотентности. Backend определяет, является ли текущая прокрутка ещё не использованным приветственным спином: в таком случае награда выбирается из `welcome_reward_items`; иначе — из активного колеса по обычным весам. Отдельный публичный эндпоинт `/spins/welcome` не требуется.

API не принимает от клиента выбранный выигрыш или размер списания. Клиент получает от сервера ID результата/сектора и анимирует колесо до соответствующего сектора.

### 9.3. Медиа

| Метод | Эндпоинт | Назначение |
|---|---|---|
| `GET` | `/api/v1/media/{media_id}/preview` | Отдать небольшое превью после проверки доступа к карточке |
| `POST` | `/api/v1/inventory/{item_id}/deliver` | Запросить отправку выигранного видео/файла в чат бота, если оно ещё не выдано или пользователь нажал повторную отправку |
| `GET` | `/api/v1/inventory/{item_id}/delivery-status` | Получить статус отправки медиа |

Токен бота и Telegram-адреса скачивания с токеном остаются только на backend. Для фотографий можно использовать защищённый proxy-маршрут; видео преимущественно доставляется ботом по сохранённому `file_id`.

### 9.4. Админка

| Метод | Эндпоинт | Назначение |
|---|---|---|
| `GET` | `/api/v1/admin/dashboard` | Краткая сводка по пользователям и игровой активности |
| `GET` | `/api/v1/admin/analytics/revenue` | Финансовый дашборд: реальная выручка, покупки и показатели по пользователям; в бете реальные поступления равны нулю, тестовые операции отдельны |
| `GET` | `/api/v1/admin/users` | Поиск/список пользователей |
| `GET` | `/api/v1/admin/users/{user_id}` | Балансы, история операций, спинов и покупок конкретного пользователя |
| `POST` | `/api/v1/admin/users/{user_id}/balance-adjustments` | Начислить/скорректировать тестовые звёзды или общий баланс спинов, с обязательной причиной |
| `GET` | `/api/v1/admin/media` | Получить медиатеку |
| `POST` | `/api/v1/admin/media/upload` | Загрузить фото/видео, обработать файл и сохранить в Telegram |
| `POST` | `/api/v1/admin/content` | Создать карточку контента |
| `PATCH` | `/api/v1/admin/content/{content_id}` | Изменить карточку или её статус |
| `GET` | `/api/v1/admin/wheels` | Список рулеток |
| `PUT` | `/api/v1/admin/wheels/{wheel_id}/segments` | Сохранить сектора и их веса |
| `GET` | `/api/v1/admin/welcome-pool` | Получить настроенный список приветственных карточек |
| `PUT` | `/api/v1/admin/welcome-pool` | Изменить список карточек для приветственного спина |
| `GET` | `/api/v1/admin/spin-packages` | Получить пакеты спинов |
| `POST`/`PATCH` | `/api/v1/admin/spin-packages` и `/api/v1/admin/spin-packages/{package_id}` | Создать и редактировать пакеты |

Пример тела запроса на корректировку баланса:

```json
{
  "resource": "SPINS",
  "amount": 5,
  "note": "Тестирование первой версии"
}
```

`resource` принимает `SPINS` или `TEST_STARS`; знак `amount` указывает на начисление или списание. Нельзя допускать отрицательного остатка. Каждая операция логируется.

### 9.5. Заготовки на будущее, не активные в MVP

Схема предусматривает `orders` и `payment_attempts`, но реальных платёжных эндпоинтов в первом рабочем релизе нет. Позднее появится обработка оплаты Telegram Stars: создание заказа/инвойса, подтверждение `successful_payment`, защита от повторной обработки и выдача ресурса. Внешний платёжный адаптер может быть добавлен в будущем только после отдельной проверки разрешённости сценария.

## 10. Развёртывание

1. Разработка и тестирование локально на Windows.
2. Для открытия Mini App в Telegram использовать HTTPS-адрес, предоставленный подходящим туннелем или тестовым хостингом.
3. Попробовать бесплатный Python-хостинг для прототипа.
4. Перед выбором проверить: доступность постоянной БД, поведение при простое, ограничения памяти/CPU, лимиты трафика, фоновые задачи, логи и правила бесплатного тарифа.
5. Не хранить единственную копию данных в локальной файловой системе бесплатного веб-сервиса: у некоторых бесплатных тарифов диск эфемерный или тестовая БД имеет ограниченный срок жизни. Медиа хранятся в Telegram, база и конфигурация регулярно резервируются.
6. При переходе к более устойчивому запуску настроить PostgreSQL, HTTPS, секреты, резервное копирование и мониторинг ошибок.

Например, в документации Render указано, что бесплатные веб-сервисы не подходят для production и не сохраняют изменения локальной файловой системы между перезапусками; условия бесплатных тарифов могут меняться. Это пример ограничений, а не окончательный выбор хостинга: провайдера выберем перед деплоем.

Ссылка: [Render — Free services and limitations](https://render.com/docs/free).

## 11. Требования к надёжности и тестированию

- Балансы, начисления, покупка пакета и списание спина выполняются транзакционно.
- Повторный запрос не приводит к дублированию операции.
- Результат спина сохраняется до запуска анимации.
- Отключённая карточка не может выпасть.
- В приветственном пуле есть только допустимые карточки активного колеса.
- После перезапуска приложения баланс, история и инвентарь не теряются.
- Ошибка отправки видео не создаёт повторный выигрыш и не возвращает уже потраченный спин автоматически; доставка может быть повторена отдельно.
- Секреты недоступны frontend.
- Пользователь не может вызвать административный API.
- Пользователь не видит агрегированную сумму своих расходов.
- В админке есть аудит изменения балансов и настроек колеса.
- В финансовом дашборде тестовые звёзды не учитываются как реальные доходы.

## 12. Критерии готовности MVP

- [ ] Бот открывает Mini App.
- [ ] Владелец видит админку, обычный пользователь — игру.
- [ ] На первой регистрации пользователю ровно один раз начисляется приветственный спин на общий баланс спинов.
- [ ] Владелец может выбрать несколько допустимых карточек для приветственной награды.
- [ ] Первый спин визуально использует полное основное колесо, но сервер выбирает выигрыш из приветственного пула.
- [ ] Все последующие спины выбираются по весам активных секторов.
- [ ] Анимация всегда заканчивается на реальном серверном результате.
- [ ] Владелец может вручную начислять тестовые звёзды и общий баланс спинов.
- [ ] Пользователь может тратить тестовые звёзды на покупку пакета спинов.
- [ ] Один спин уменьшает общий баланс доступных спинов ровно на единицу.
- [ ] Карточки и результаты сохраняются; коллекция доступна после повторного входа.
- [ ] Фото оптимизируются для Telegram и Mini App; токен бота не раскрывается клиенту.
- [ ] Выигранное видео доставляется сообщением бота и его можно повторно запросить из коллекции.
- [ ] Админка показывает игровую статистику и отдельный финансовый дашборд; тестовые операции обозначены отдельно от реальной выручки.
- [ ] Платежи Stars и интеграция Dropp.fans не активны в MVP.

1. Создать структуру проекта и конфигурацию локального окружения.
2. Создать модели SQLAlchemy и первую миграцию БД.
3. Поднять FastAPI и базовый Telegram-бот на aiogram.
4. Реализовать авторизацию по Telegram `initData` и разделение ролей.
5. Реализовать балансы, транзакции и начисление приветственного спина.
6. Реализовать медиатеку, карточки, колесо и серверную механику спина.
7. Реализовать покупку пакетов за тестовые звёзды, коллекцию и доставку видео.
8. Реализовать админку, статистику и тесты критичных сценариев.
9. Проверить бесплатный хостинг и перенести прототип, не теряя данные.
